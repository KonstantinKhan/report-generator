# Форматирование таблицы спецификации (ЕСКД §1)

> **Частично устарело (2026-10-03).** Вид таблицы и алгоритм раскладки описаны верно, но правила данных и стиль теперь живут
> в `gost-spec.yaml` (блок `body`), а не в `Specification.kt`; границы ячеек рисуются линиями, а не `Rectangle`; у
> дозаполнения страницы есть режим `remainder` и нижняя граница последней строки рисуется всегда. Актуальная справка:
> [template-yaml.md](template-yaml.md#таблица-потока-flow--table). Отмеченные ниже места исправлены, историческое описание
> сохранено.

Таблица спецификации состоит из секций (порядок = `groupBy.order` в `gost-spec.yaml`, ГОСТ Р 2.106-2019 §1). Модель
(`SpecificationData` в `reports/specification`) хранит 7 секций, у каждой свой тип элемента:
1. **Документация** (`documentation`, `DocumentationItem`; позиции и "Кол." нет)
2. **Сборочные единицы** (СЕ, `assemblies`, `AssemblyItem`)
3. **Детали** (`parts`, `PartItem`)
4. **Стандартные изделия** (`standards`, `StandardItem`)
5. **Прочие изделия** (`others`, `OtherItem`)
6. **Материалы** (`materials`, `MaterialItem`)
7. **Комплекты** (`kits`, `KitItem`; см. «Комплекты» ниже). Комплекты без Спецификации выводятся блоками состава (`kitBlocks`,
   `KitBlock`) в этом же разделе

Секции **Комплексы** и **Программные изделия и базы данных** в модель пока не введены (нет требований): узлы видов
Complex и Software при маппинге пропускаются без ошибки и в отчёт не попадают. Заголовков этих секций в `gost-spec.yaml` нет.

**Позиция** ("Поз.") берётся из данных элемента (позиция связи в Loodsman), а не нумеруется заново, и только
выводится: порядок строк внутри секции от неё не зависит (см. «Порядок строк внутри секции»). Элемент без позиции даёт
пустую ячейку. Документация сортируется по обозначению, без него по наименованию.

### Порядок строк внутри секции

Порядок задаёт `SpecificationOrder` (`reports/specification`), применяется в `ProductNode.toSpecificationData()` при сборке
секций; YAML (`sortBy`) порядок не меняет. Те же функции собирают секции основной части, блоков исполнений и блоков
комплектов без Спецификации, поэтому правила везде одни. Сортировка устойчивая: равные по правилам строки идут в порядке
связей.
- Сборочные единицы, детали: обозначение (пустое после непустого), затем наименование.
- Материалы: вид материала по ЕСКД (атрибут «Вид материала по ЕСКД», у формы материала берётся с её материала), затем
  наименование, затем обозначение. Порядок видов фиксирован: металлы черные; магнитоэлектрические и ферромагнитные;
  цветные, благородные и редкие; кабели, провода и шнуры; пластмассы и пресс-материалы; бумажные и текстильные;
  лесоматериалы; резиновые и кожевенные; минеральные, керамические и стеклянные; лаки, краски, нефтепродукты и химикаты;
  порошки; прочие. Вид не из списка или пустой - в конец. Сравнение без учёта регистра и пробелов по краям.
- Стандартные и прочие изделия: категория по префиксу атрибута «Обозначение стандарта»: ГОСТ, ГОСТ Р, ОСТ, ТУ, DIN
  (`standardCategoryIndex`, `StandardCategory.kt`: «ГОСТ Р» проверяется раньше «ГОСТ», после префикса не буква или конец).
  Внутри категории: вид изделия («Вид изделия», пустой в конец категории), обозначение стандарта, типоразмер
  («Типоразмер»), наименование. Без распознанной категории: хвост секции, плоско по наименованию, затем по обозначению.
- Типоразмер: разделители `x`, `х`, `×`, `X`, `Х` между цифрами или пробелами заменяются пробелом; числа с дробной частью
  (`3,2`, `28.4`) сравниваются как десятичные. Десятичная логика только у типоразмера.
- Документация (по обозначению), комплекты (по позиции связи, затем по обозначению) и порядок исполнений (естественный
  порядок обозначений, `NaturalOrder`) остались как были.
- Нет данных новых атрибутов (поля `null`): сортировка деградирует до наименования и обозначения.

Естественный порядок строк (`NaturalStringOrder`): строка делится на куски из букв и цифр, разделители отбрасываются.
Буквенный кусок раньше цифрового; цифровые куски сравниваются как числа (`-2` раньше `-10`); регистр не учитывается;
кириллица раньше латиницы; `Ё` сразу после `Е`; при равных общих кусках короткая последовательность раньше
(`АБВГ.301234.002` раньше `АБВГ.301234.002-01`).

Поля `materialKind` (`MaterialItem`) и `standardDesignation`, `productKind`, `sizeType` (`StandardItem`, `OtherItem`, общий
`CatalogItem`) заполняются из атрибутов узла, пустое значение это `null`. В колонках таблицы они не выводятся.

### Подзаголовки видов изделий

Для секций «Стандартные изделия» и «Прочие изделия» адаптер `SpecificationDataContext` записывает в строку `item`
необязательное поле `subgroup` (String): множественное число вида изделия из словаря
`reports/specification/src/main/resources/product-kind-plurals.yaml` (`SpecificationSubgroups`). Поле есть только если
категория стандарта распознана (то же определение, что в сортировке) и «Вид изделия» есть в словаре. Иначе поля нет и
заголовка нет: вид не из словаря, пустой вид, нераспознанная категория, другие секции.

Словарь: плоский YAML `единственное число: Множественное`, ключ без учёта регистра и пробелов по краям. Стартовый набор:
Болт, Винт, Гайка, Шайба, Шплинт, Шпилька, Штифт, Шпонка, Заклепка, Кольцо, Подшипник, Манжета, Гвоздь, Саморез, Анкер.
Файл разбирается собственным разбором плоской карты (`kaml` не входит в compile-зависимости модуля).

В `gost-spec.yaml` включена опция `subTitle: {field: subgroup, column: name, style: groupTitle, align: center}`
(см. [template-yaml.md](template-yaml.md)). Строка-заголовок: подчёркнутый стиль по центру колонки «Наименование», без
пустых строк до и после, без номера «Поз.», не входит в итоги, привязана к первой строке своего вида (не остаётся одна
внизу страницы). Заголовок ставится на смене значения внутри секции. Ограничение: один вид подряд в конце одной
категории и в начале следующей («Болты» ГОСТ и «Болты» DIN без других видов между ними) заголовок не повторяет.

Тесты: `SpecificationOrderTest`, `SpecificationSubgroupsTest`, `SubgroupsGoldenTest` (golden `spec-subgroups.txt`).

Пустая секция (нет элементов) в документе не появляется — ни заголовка, ни спейсеров.

## Правила формата и примечаний спецификации

**Формат** (первая колонка, "Формат") выводится для документации, сборочных единиц и деталей. Документация (сборочный чертёж
корня) берёт «Формат» из собственных атрибутов документа. Для сборочных единиц и деталей источник — документ элемента
(`Usage.target.usages`, `DocumentUsage`): сборочная единица — первый документ вида «Спецификация» с непустым «Формат»,
деталь — первый документ вида «Чертёж детали» с непустым «Формат». Нет документа, нет формата или формат не загружен —
ячейка пустая (ошибки нет).
- **Простой** формат (`A0`…`A4`, любая строка без буквы x) кладётся в колонку как есть, в примечания не дублируется.
- **Сложный** формат — строка с символом `x`/`X` (латиница) или `х`/`Х` (кириллица), напр. `А3х3`: в колонке `*)`,
  первой строкой примечаний идёт `*)А3х3` (без пробела после `*)`).
- **Сложная** зона — значение с запятой (несколько зон), напр. `7B, 8C`: в колонке `*)`, в примечаниях `*)7B, 8C` (после
  примечания формата, до примечания состава). Зона читается из атрибута связи «Зона».

**Пустое количество.** Неосновной член допускаемой замены не имеет количества в колонке «Кол.» (`quantity = null` в
`SpecificationData`, в шаблоне ячейка `optional`); его количество — первое примечание (см. «Допускаемые замены»). Для
остальных строк и для спецификаций без замен поведение прежнее.

**Количество в диапазоне** (`Quantity.Range`, у связи заданы разные min и max): в колонку «Кол.» выводится минимум, в
примечания — строка `Наиб. кол. <max>` (после сносок формата и зоны, до примечания состава). Максимум материала — как
есть, с десятичной запятой и без хвостовых нулей; у остальных секций — целое, округление half up, как в колонке «Кол.».
Если min = max, это точное количество, примечания нет.

**Примечание** (колонка "Примечание", `notes`, одна строка на запись; в ячейке строки через перенос):
- сборочная единица и деталь: `[*)<сложный формат>, если есть] + [*)<сложная зона>, если есть] + [Примечание состава, если есть] + [Способ применения, если есть] + [тексты замен]`;
- стандартное и прочее изделие: `[*)<сложная зона>, если есть] + [Примечание состава, если есть] + [Способ применения, если есть] + [тексты замен]`;
- материал: `[единица измерения, если есть] + [*)<сложная зона>, если есть] + [Примечание состава, если есть] + [Способ применения, если есть] + [тексты замен]` — единица кол-ва (напр. "кг", "м")
  всегда первой строкой; в "Кол." единицу не пишем (колонка 10 мм, значение + единица не помещаются в одну строку).

Примечание состава — атрибут связи «Состоит из» с ключом `note` (`LinkAttributeKey.Note`, в Loodsman «Примечание»).
Способ применения — атрибут связи «Состоит из» с ключом `applicationMethod` (`LinkAttributeKey.ApplicationMethod`, в Loodsman
«Способ применения»); попадает в примечание только у члена производственной группы замен (см. «Допускаемые замены»).
Пустое или пробельное значение записи не даёт, не загруженное значение — тоже (запрос примечаний — часть
`specificationQuery`). Пустые строки в `notes` не попадают.

Колонка «Примечание» выровнена по левому краю (`align: left` в `gost-spec.yaml`); заголовок «Примечание» — по центру.

**Количество материалов** выводится без округления: `1,254` остаётся `1,254`, `0,004` — `0,004`, `3.0` — `3`, `6.2E-33` —
полной десятичной записью (`0,0000…62`, не научной нотацией). Ограничение — число знаков в `pattern` (60). Колонка «Кол.» 10 мм:
длинное значение переносится по символам, строка таблицы растёт (например, `1234567,891` занимает 3 строки, `6.2E-33` — 10).

**Стандартные и прочие изделия** (`standards`, `others`): столбец «Обозначение» берётся из атрибута Loodsman «Обозначение
изделия» (`AttributeKey.ProductDesignation`), столбец «Наименование» — из «Обозначения» (ключевой атрибут типа, полное
обозначение изделия, напр. «Подшипник 411 ГОСТ 520-2011»). Атрибут «Наименование» у этих видов не используется. Формат не
выводится. Нет «Обозначения изделия» — столбец «Обозначение» пуст, ошибки нет. Нет «Обозначения» (или не загружено) —
`SpecificationDataException`. Это правило `standardDesignationAndName()` в `ProductNodeSpecification.kt`; для сборочных
единиц, деталей и материалов оно не меняется. Подробности — [loodsman-integration.md](loodsman-integration.md#правила-преобразования-в-спецификацию).

**Материалы**: обозначение выводится в столбец «Наименование», столбец обозначения пуст. Это правило конвертера
`PdmNode.toSpecificationData()` (`reports/specification`), подробности — [loodsman-integration.md](loodsman-integration.md#правила-преобразования-в-спецификацию).

**Материал через форму материала.** Форма (вид «Форма материала») попадает в раздел «Материалы» вместе с обычными
материалами и сортируется с ними по тем же правилам. Наименование берётся у материала, связанного с формой по
«Изготавливается из ...», позиция, количество, единица и примечание — у связи формы в сборочной единице. Если у формы
несколько материалов, выводится первый. Форма без материала — ошибка спецификации (`SpecificationDataException` с id формы),
а не пустая строка.

**Допускаемые замены (группы замен корня).** Тексты замен берутся только из групп типа «Допускаемая замена» (`ReplacementType.Permissible`) у корня (`PdmNode.replacements`
корня, запрос `specificationQuery`: `replacements = true`, `replacementDepth = 0`). Группы «Производство» дают только
«Способ применения» (см. ниже); группы «Потребитель» не влияют на спецификацию: их члены — обычные строки.
Член группы сопоставляется с связью состава корня по `linkId`, позиция берётся у этой связи. Нет позиции у члена
допускаемой группы — `SpecificationDataException` (ошибка данных). Логика — `ReplacementNotes.kt`.

**Производственные группы** (`ReplacementType.Production`, в UI «Производственная»): не дают текстов замен и не влияют на
количество и позицию строки. Для каждого члена, который является связью состава корня, значение атрибута связи «Способ
применения» (`applicationMethod`) добавляется в примечание строки. Пустое или пробельное значение, отсутствие атрибута и
член не из состава корня — пропускаются. Исключений для этих групп нет: число базовых вариантов не проверяется. Если член
есть и в производственной, и в допускаемой группе, у него работают обе части: значение и тексты замен.
Группы «Потребитель» (`ReplacementType.Consumer`) не учитываются: их члены — обычные строки.

**Отбор членов.** В `PdmNode.replacements` приходят все члены групп (см. [loodsman-integration.md](loodsman-integration.md#группы-замен-допускаемые-замены)),
спецификация отбирает их сама:
- Сырая группа должна иметь ровно один базовый вариант; иначе — `SpecificationDataException` (ошибка данных).
- Член, чей `linkId` не является связью состава корня, игнорируется (ошибки нет); его позиции в группе нет.
- Варианты, оставшиеся без членов, отбрасываются.
- **Группа пропускается молча**, если базовый вариант не содержит ни одного члена состава корня или не осталось
  ни одного неосновного варианта. Её оставшиеся члены выводятся обычными строками без примечаний замены.
- Неосновной вариант, присутствующий частично, учитывается только своими членами: позиции фрагментов и «взамен поз. …»
  строятся по присутствующим членам.

- **Базовый вариант** группы (`basic`): каждый его член получает примечание
  `допуск. замена на поз. <…>`. Фрагмент на каждый неосновной вариант группы: `поз. <min позиция варианта>`, если в
  варианте несколько членов, добавляется ` совместно с поз. <остальные позиции по возрастанию>`. Фрагменты вариантов
  соединяются через ` или `; «на» пишется один раз. Пример: вариант «Болт + Шплинт» (поз. 7 и 8) вместо поз. 5 —
  `допуск. замена на поз. 7 совместно с поз. 8`. Если узел базовый в нескольких группах, фрагменты всех групп
  идут через ` или `. Группа без неосновных вариантов ничего не выводит.
- **Неосновной вариант** группы: каждый член получает примечание `примен. [с поз. <остальные члены варианта> ]взамен поз. <
  позиции базового варианта>`, напр. `примен. с поз. 8 взамен поз. 5`. Если член в нескольких группах, тексты групп
  соединяются через ` или ` после одного `примен. `: `примен. с поз. 8 взамен поз. 5 или взамен поз. 6`.
- Один и тот же узел может быть базовым в одной группе и неосновным в другой: получает оба примечания отдельными
  записями (сначала «допуск.», потом «примен.»).
- **Неосновной член** выводится в спецификацию иначе:
  - **Количество пусто** (колонка «Кол.»); количество (минимум диапазона) выводится первым примечанием: `N шт.`
    (у материала вместо `шт.` — единица измерения, если она есть; тогда отдельной строки единицы в примечаниях нет).
  - Далее обычные примечания (формат, зона, `Наиб. кол. <max>`, примечание состава), затем тексты замен.
- **Порядок примечаний** любой строки: `N шт.` (только неосновной), обычные примечания, «Способ применения» (только
  производственный член), тексты замен. Текст базового члена начинается с заглавной буквы («Допуск. замена …») только тогда,
  когда он первое примечание строки; «примен.» всегда строчными.

Пример (объект с болтом поз. 5, его заменой «Болт 2 + Шплинт» поз. 7 и 8):

| Поз. | Кол. | Примечание |
|------|------|------------|
| 5 | 4 | Допуск. замена на поз. 7 совместно с поз. 8 |
| 7 | — | 4 шт. / примен. с поз. 8 взамен поз. 5 |
| 8 | — | 4 шт. / примен. с поз. 7 взамен поз. 5 |

Строки группы «Потребитель» (поз. 9) выводятся обычно, с количеством и без примечаний замен. Строка группы «Производство»
(поз. 10) выводится с количеством, без текстов замен; если у связи задан «Способ применения» (напр. «Окраска»), он
идёт в примечание: `Окраска`.

Каждый блок:
- Начинается с заголовка (курсив, 3.5мм, подчёркнут)
- Предваряется 2 пустыми строками (спэйсер *before*)
- Следуется 1 пустой строкой (спэйсер *after*)
- Содержит строки данных с фиксированной высотой 8мм

**Где живут константы.** Структура и стиль таблицы (ширины колонок, `stick`, тексты и стили шапки, высота
строки 8 мм, число пустых строк до/после заголовка, колонка заголовка группы, заполнение страницы, цепочка
заголовка, `bind` каждой ячейки строки) и ПРАВИЛА данных (заголовки и порядок секций `groupBy` по полю `section`, вывод
позиции из `item.position`, формат количества `format` + `cases`: материалы без округления (`pattern` `0.` + 60 знаков `#`, запятая, хвостовые нули срезаны), остальные целое HALF_UP,
выравнивание колонки «Примечание» по левому краю (`align: left`, заголовок остаётся по центру),
вывод колонок «Формат» и «Примечание» как есть из `item.format` / `item.notes`) описаны в блоке `body` (`type: flow`, секция `table:`) файла
`report-ir/src/main/resources/templates/gost-spec.yaml`. Кодом остаются только данные: `Specification.kt` собирает
`DataContext` и вызывает `FlowTables.build`, `SpecificationDataContext.kt` отдаёт сырые поля записи. Алгоритм (измерение, перенос,
пагинация, дозаполнение) остаётся кодом `report-layout`. Справка по YAML: `template-yaml.md`, раздел
«Таблица потока».

Все строки (заголовок, данные, пустые) имеют **тонкие границы** на каждой ячейке
(ГОСТ 2.303: 0.7pt ≈ 0.247mm, ~S/3 от основной линии).

## Комплекты

Комплект (узел вида `Kit`, связь «Состоит из ...») попадает в секцию **Комплекты** (`kits`, `KitItem`) после «Материалов»
(`groupBy.order`: KIT последним, заголовок «Комплекты»), если выполнены оба условия:
- у связи нет непустого «Назначения комплекта» (см. «Хвост таблицы: примечания комплектов»);
- у комплекта есть документ вида «Спецификация» (связь «Документы», `DocumentUsage` с видом `Specification`).

Строка комплекта — как у сборочной единицы: поз., обозначение, наименование, кол., зона, формат (формат документа
«Спецификация» комплекта), примечание (`*)`-формат, `*)`-зона, «Наиб. кол.», примечание состава, способ применения,
тексты замен). Комплект участвует в сравнении исполнений как обычный элемент (см. «Переменные данные для исполнений»).

### Блоки комплектов без Спецификации

Комплект без непустого «Назначения комплекта» и без документа «Спецификация» не попадает в строки комплектов, а выводится
**блоком** своего состава. Блок идёт в той же таблице, в разделе «Комплекты»:
- 3 пустые строки без объединения колонок;
- строка с наименованием комплекта в колонке «Наименование» (стиль и выравнивание заголовка группы);
- 1 пустая строка;
- разделы состава комплекта (Документация, Сборочные единицы, Детали, Стандартные изделия, Прочие изделия, Материалы) —
  группы с заголовками и спейсерами, как в основной таблице.

Пустые строки перед блоком, наименование, пустая строка и первая строка данных держатся вместе (не разрываются
страницей). Состав читается по правилам основной таблицы: строки, примечания, замены, способ применения.

Порядок:
- блоки идут **после** строк комплектов со Спецификацией (группа KIT);
- блоки отсортированы по позиции связи комплекта в корне, затем по обозначению, без обозначения по наименованию.

Заголовок «Комплекты»: если в таблице нет строк комплектов со Спецификацией, а блоки есть, заголовок выводится явно —
2 пустые строки, строка заголовка в стиле заголовка группы, 1 пустая строка (как у заголовка группы). Иначе группа KIT
выводит его сама.

Исполнения: комплект сравнивается между исполнениями как обычный элемент (обозначение и количество связи). Общий комплект
выводится в основной части, необщий — в блоке каждого исполнения, в котором он есть, после групп этого исполнения.

Количество самого комплекта нигде не показывается и не умножает состав. Комплект без состава (после фильтров ни одной
строки) блока не даёт. Комплект внутри такого комплекта не выводится (см. [known-gaps.md](known-gaps.md)).

### Комплекты документов

Комплект документов (узел вида `DocumentSet`, связь «Состоит из ...») попадает в строку раздела «Комплекты» (`kits`,
`KitItem`), если у него по связи «Документы» есть объект вида «Ведомость эксплуатационных документов»
(`OperationalDocumentsList`, первый найденный). Без ведомости комплект документов нигде не выводится и не участвует в
сравнении исполнений.

С непустым «Назначением комплекта» (связь «Состоит из ...», `kitPurpose`) комплект документов не выводится ни в строке
раздела «Комплекты», ни в блоках исполнений, не участвует в сравнении исполнений и даёт примечание в хвосте таблицы
(см. ниже). Ведомость для примечания не нужна: примечание выводится и без неё. Обозначение и наименование в примечании —
атрибуты самого комплекта документов, не ведомости. Пустое (blank) значение — то же, что его отсутствие.

Строка комплекта документов:
- обозначение — атрибут «Обозначение» ведомости;
- наименование — атрибут «Наименование изделия» ведомости (не «Наименование»); без обозначения — только наименование;
- формат — атрибут «Формат» ведомости, как есть (без выноски `*)`);
- количество — обычное количество связи «Состоит из ...» (`CompositionUsage.quantity`, как у остальных элементов состава):
  точное значение или нижняя граница диапазона «Мин./Макс.»; верхняя граница примечанием не выводится. Пустое
  (`Quantity.Missing`) или не загруженное (`Quantity.NotLoaded`) количество — `SpecificationDataException` с сообщением об узле;
- поз. и зона пустые, примечаний нет (`notes` пусто).

Строка идёт в тот же список, что строки комплектов со Спецификацией, и сортируется так же (комплекты сортируются по
позиции, а не по правилам `SpecificationOrder`): с позицией — по позиции,
без позиции (у строки комплекта документов позиции нет) — после позиционных, по обозначению, без него по наименованию.

Исполнения: ключ сравнения — id комплекта документов и количество связи целиком (точное значение или диапазон «Мин./Макс.»),
как у остальных элементов состава. Общий комплект документов остаётся в основной части, необщий — в блоке каждого
исполнения, как остальные элементы.

Комплект документов внутри комплекта (блока или Спецификации) не выводится (см. [known-gaps.md](known-gaps.md)).

## Хвост таблицы: примечания комплектов

Комплект или комплект документов с непустым «Назначением комплекта» (связь «Состоит из ...», атрибут `kitPurpose`,
`LinkAttributeKey.KitPurpose`, relation COMPOSITION) не выводится ни в одной секции: ни в основной части, ни в блоках
исполнений. Вместо него создаётся примечание с текстом:

`Примечание - <обозначение> - <наименование> <значение>`

Обозначение и наименование — атрибуты самого узла (комплекта или комплекта документов), для комплекта документов не
ведомости. Дефисы буквальные, значение через пробел. Если обозначения нет, выводится `Примечание - <наименование> <значение>`.
Примечания собираются из корня и всех исполнений, без повторов по паре (id узла, значение): сначала корень, затем
исполнения в порядке блоков, внутри — порядок связей.

Вывод: после блока «Переменные данные для исполнений» (а если блока нет — после основной части):
- 2 пустые строки без объединения колонок;
- каждое примечание отдельной строкой, объединяющей колонки «Обозначение»..«Наименование» (как заголовок исполнений);
  строки идут подряд, без отступов.

Нет примечаний — хвост не выводится. Формат задан кодом (`FlowNotes` в `report-ir`, `kitNoteTail()` в
`reports/specification`). Длинный текст переносится по ширине объединённых колонок (раскладка `spanRowBlocks`); рендер такого
текста в живом документе не проверен.

## Переменные данные для исполнений

Раздел печатается в конце спецификации, только если есть хотя бы один блок исполнения с уникальными элементами
(правила сравнения — в [loodsman-integration.md](loodsman-integration.md#правила-преобразования-в-спецификацию), пункт (д)).
Без блоков раздел не печатается, и спецификация не меняется.

- 3 пустые строки после основной части.
- Заголовок «Переменные данные для исполнений» по центру, объединённая ячейка **только** колонок «Обозначение» и
  «Наименование» (`IrSpanRow`, `titleFrom` = `designation`, `titleTo` = `name`). Остальные колонки строки заголовка
  (Формат, Зона, Поз., Кол., Примечание) остаются отдельными ячейками со своими вертикальными линиями, как в обычных
  строках; внутри объединённой ячейки линии нет. Раскладка: `spanRowBlocks` в `TableMeasurement.kt` (`report-layout`)
  строит строку по колонкам таблицы, где диапазон `from..to` схлопнут в одну колонку только для ширины и переноса текста.
  Раньше строка заголовка рисовала один прямоугольник без линий у остальных колонок.
- Порядок блоков: основное исполнение (корень) первым, остальные по обозначению (`designation`) в натуральном порядке
  (`NaturalOrder` в `ProductNodeSpecification.kt`): отрезки цифр сравниваются как числа, `«-2» < «-10»`; регистр не важен;
  при равных обозначениях сохраняется порядок связей «Исполнения» (сортировка стабильна). Сортировка одна, в
  `toSpecificationData()`.
- Для каждого блока (порядок см. выше): пустая строка,
  обозначение исполнения в колонке «Наименование» (`FlowAppendixBlock.label`), пустая строка; далее подразделы, как в основной
  части (Документация, Сборочные единицы, Детали, Стандартные, Прочие, Материалы), по тем же правилам `groupBy` и `skipEmpty`.
  Пустой подраздел не печатается.
- После последней записи блока — 2 пустые строки. Между блоками отступы суммируются: 2 + 1 = 3 пустые строки.
- Заголовок раздела, пустые строки и обозначение исполнения держатся вместе с первой строкой своего блока (цепочка
  `keepWithNext`), они не остаются внизу страницы. Подразделы держатся по `keep.titleChain` основной таблицы.

Формат задан кодом (`FlowAppendix` в `report-ir`, `variantAppendix()` в `reports/specification`), не YAML:
отступы и заголовок фиксированы правилом раздела, а колонки, стили групп и `groupBy` берутся из `gost-spec.yaml` как у основной части.

## Архитектура реализации

### IR уровень (`report-ir`)

**`TextStyle`** — добавлено:
```kotlin
data class TextStyle(
    val fontFamily: String,
    val fontSizeMm: Double,
    val bold: Boolean = false,
    val italic: Boolean = false,    // ← new
    val underline: Boolean = false  // ← new
)
```

Оба поля `italic`/`underline` — семантические метки (не гарантируют наличие
шрифта в конкретной гарнитуре). Рендер будет синтетическим.

**`IrTable`**:
```kotlin
data class IrTable(
    val columns: List<IrColumn>,
    val header: IrTableHeader?,
    val content: List<IrTableElement>,
    val style: TableStyle = ...,
    val rowHeight: Length? = null,
    val groupTitle: IrGroupTitle = IrGroupTitle(),   // заменил groupTitleColumn
    val fillBlank: Boolean = true,                   // только при rowHeight != null
    val fillRemainder: IrFillRemainder = STRETCH,    // остаток высоты на странице 1: STRETCH (в последнюю строку) | GAP (зазор)
    val fillRemainderRest: IrFillRemainder = fillRemainder, // то же для страниц 2+ (по умолчанию как на странице 1)
    val footer: List<IrTotalRow> = emptyList(),      // итоги таблицы, только при rowHeight != null
    val lineNumbers: IrLineNumbers? = null           // нумерация физических строк (`${line.number}`), только при rowHeight != null
)
```

- `rowHeight = null` → автовысота (старое поведение, обратная совместимость)
- `rowHeight = 8.mm` → **фиксированная** высота, word-wrap в физические строки
- `groupTitle.column = "name"` → заголовок группы помещается **в одну колонку**
  (не full-width спан, это `column = null`), остальные колонки остаются пусты;
  `spacerBefore` / `spacerAfter` (по умолчанию 2 / 1), `style`, `align`, `keepWithRows` (цепочка заголовка)
- `fillBlank` — дозаполнять страницу пустыми строками (`fill: blank` в YAML)
- `fillRemainder` / `fillRemainderRest` — что делать с высотой страницы, оставшейся после последней целой пустой строки:
  режим страницы 1 и страниц 2+ соответственно. В YAML `remainder: stretch|gap` (обе части сразу) или `remainder: {first, rest}`
  (см. «Остаток высоты при `fill: blank`» в `template-yaml.md`). `STRETCH`: остаток уходит в последнюю строку страницы;
  если места под пустую строку нет совсем, растягивается последняя строка данных страницы. `GAP`: последняя строка обычной высоты, под ней зазор
- `IrGroup.footer` / `IrTable.footer` — строки итогов (`IrTotalRow(cells)`, по ячейке на колонку): подвал группы после
  её строк данных, подвал таблицы после последней группы и до пустого дозаполнения. Строка итога рисуется как обычная
  строка с границами; движок привязывает её цепочкой `keepWithNext` к последней строке, которую она итожит (см. «Итоги»
  в `template-yaml.md`)
- `IrTableHeader.repeat` — шапка на каждой странице (по умолчанию да); `false`: только на первой,
  остальные страницы начинаются у верхнего поля
- Текст шапки хранится только в `IrTableHeader.cells`; поле `IrColumn.header` удалено (дубль)
- Эту структуру собирает `FlowTables.build(spec, schema, rows)` из YAML-описания и записей `item` (правила в YAML)

**Стили**:
```kotlin
object Styles {
    val groupHeader = TextStyle(
        fontFamily = FontFamilies.GOST_TYPE_B,
        fontSizeMm = 3.5,
        italic = true,      // синтетический наклон
        underline = true    // геометрический подчёркивающий Line элемент
    )
    val tableBorderThin = BorderStyle(widthPt = 0.7)
}
```

### Layout уровень (`report-layout`)

#### Разделение на физические строки

**`splitRowIntoPhysicalRows(row, columns, offsets, textMeasurer, rowHeight)`**:
1. Для каждой ячейки → `textMeasurer.measure(cell.text, style, cellTextWidth(columnWidth), breakLongWords = true)`
   (word-wrap по словам внутри `PdfBoxTextMeasurer`). Доступная ширина
   `cellTextWidth` = ширина колонки минус `FRAME_CELL_PADDING` (1 мм) **с обеих сторон**,
   для любого выравнивания: LEFT-текст рисуется с отступом 1 мм от левой границы, и без
   правого отступа строка упиралась бы в правую границу. Пустые "слова" от двойных
   пробелов пропускаются. Слово шире доступной ширины (длинное обозначение без пробелов)
   **рвётся по символам** (без дефиса), строка никогда не выходит за границу ячейки.
   `breakLongWords` включён только для тела таблицы; ячейки рамки/штампа не ломают слова
   (напр. "Изм" в узкой ячейке штампа)
2. `physicalRowCount = max(1, cells.maxOf { lines.size })`
3. Итого `physicalRowCount` объектов `MeasuredRow`, каждый высотой ровно `rowHeight`
4. На физической строке `k`:
   - Для колонок, где `lines.size > k`: строка `lines[k]`
   - Для колонок, где `lines.size ≤ k`: пустая строка `""`
   - Сбоку-адаптивные столбцы типа "Поз." (один символ) имеют `lines.size = 1`,
     поэтому на `k ≥ 1` автоматически становятся пусты

#### Границы ячеек

**`drawBorderedRow(block: BorderedRowBlock, y, ...)`** — функция рендера:
1. **Для каждой колонки** четыре тонких `Line` (верх, право, низ, лево; ГОСТ 2.303). Раньше был один `Rectangle(rect, styleBorderThin)`:
   единственный `Rectangle` на странице теперь рамка листа (`c8a8cda` перевёл тесты слоя раскладки на линии)
2. **Text с паддингом**: `TextAlign.LEFT` → левый паддинг 1 мм (иначе текст спадает
   на границу), ширина переноса `cellTextWidth` (минус 1 мм справа).
   `TextAlign.CENTER` → текст центрируется по ширине колонки, перенос по той же `cellTextWidth`.
3. Вертикальное расположение текста в строке: baseline на 80% высоты
   (как в горизонтальном тексте таблицы)

**`underline = true`** — добавляется геометрический `Line` элемент под текстом:
```kotlin
Line(from = (x, y + lineHeight), to = (x + lineWidth, y + lineHeight), 
     style = LineStyle(width = 0.7pt))
```

Это НЕ трогает рендер (§12 архитектуры: рендер не решает "как"), а только
Layout IR: добавляет в `PageElement` список дополнительный `Line` рядом с
`PositionedText`.

#### Блоки и спейсеры

При `table.rowHeight != null` (в `buildBlocks`; числа 2 и 1 это `groupTitle.spacerBefore` / `spacerAfter`):
```
группа:
  2x blank (спэйсер before) [всегда keepWithNext = true]
    ↓
  GROUP_HEADER [всегда keepWithNext = true]
    ↓
  1x blank (спэйсер after) [keepWithNext = true, если у группы есть строки данных]
    ↓
  data rows (split via splitRowIntoPhysicalRows) [keepWithNext = element.constraints.keepTogether]
```

Цепочка спейсеры + заголовок + пустая строка после **unconditionally** связана с
**первой физической строкой данных**: заголовок группы не остаётся "сиротой" внизу
страницы (раньше цепочка обрывалась на пустой строке после заголовка). Остальные строки
группы привязываются друг к другу только при `keepTogether` — длинная группа не
склеивается в один неделимый блок. Группа без строк данных не привязывается к
следующей группе (в спецификации такие группы не создаются). Высота цепочки при
одностроковом заголовке: 4 строки + 1 строка данных = 5 x 8 мм = 40 мм, что много меньше
высоты любой страницы.

#### Дозаполнение страницы

В `renderPages` (`LayoutEngine.kt`):
1. Отслеживается `pageFinalY: List<Length>`: финальная Y-координата закрытой каждой страницы.
2. После основного цикла выкладки, если `table.rowHeight != null` и `table.fillBlank`, для каждой страницы:
   ```kotlin
   val available = contentBottom(page) - pageFinalY[page]
   val fullRowsCount = available / rowHeight                // целых пустых строк
   val remainder = available - rowHeight * fullRowsCount    // 0 <= остаток < rowHeight
   // STRETCH: последняя строка = rowHeight + remainder, GAP: все ровно rowHeight, остаток остаётся зазором
   ```
   Раньше при наличии рамки движок убирал нижнюю границу последней строки; теперь нижняя граница
   последней строки рисуется всегда, в обоих режимах. Подробности и пример с цифрами: `template-yaml.md`, «Остаток высоты при `fill: blank`».
3. Если контента ноль вообще (пустой документ или все блоки пусты) — `pageFinalY[0] = contentTop`, дозаполняется вся страница.
4. Нумерация физических строк (`lineNumbers`) ставится вторым проходом, после раскладки блоков по страницам, чтобы номер
   следовал итоговому месту строки.

### Renderer уровень

#### PDF (`report-render-pdf`)

**Синтетический italic** (no italic GOST Type B font loaded — см.
[fonts-and-licensing.md](fonts-and-licensing.md)):

```kotlin
private const val ITALIC_SHEAR = 0.2f  // ~11° slant, tan ≈ 0.2

fun italicMatrix(x: Float, y: Float, italic: Boolean): Matrix =
    if (italic) Matrix(1f, 0f, ITALIC_SHEAR, 1f, x, y)
    else Matrix.getTranslateInstance(x, y)
```

Применяется в `renderHorizontalText` через `stream.setTextMatrix(italicMatrix(...))`.
Горизонтальный сдвиг в матрице текста `[a b c d e f]` компонент `c` — это
косой сдвиг: `(px, py) → (px + c*py + e, d*py + f)`. При `c = 0.2`, текст
выше baseline наклоняется влево, ниже — вправо (стандартный наклон 11°).

#### SVG (`report-render-svg`)

```kotlin
val fontStyle = if (text.style.italic) """ font-style="italic"""" else ""
return """<text ... $fontStyle>${text.text}</text>"""
```

SVG имеет встроенную поддержку `font-style="italic"`, браузер сам применяет
синтетический наклон если italic-вариант не найден.

```kotlin
// Specification.kt: только данные, правила таблицы в YAML
```
