# Известные незакрытые места

Честный список того, что упрощено или не сделано — сознательно, не забыто.
Ничто из этого не блокирует дальнейшую работу, но стоит держать в голове
перед тем, как строить сверху что-то, что этих гэпов не переживёт.

## Layout Engine

- **Горизонтальный overflow не проверяется.** `LayoutOverflowException`
  ловит только вертикальное переполнение (строка/страница выше доступного
  места). Если сумма ширин колонок таблицы больше ширины контентной
  области — колонки молча вылезут за рамку страницы без ошибки. Это
  реально произошло один раз при разработке (тестовая фикстура фазы 6 со
  слишком узкой страницей) — было замечено при ревью golden-снапшота, не
  автоматической проверкой. См. `report-layout/LayoutEngine.kt`,
  `renderPages()` — там только `contentBottom` проверяется, аналога по X
  нет.
- **Минимальная высота строки данных (8мм по ГОСТ Р 2.106-2019, форма 1)
  не форсируется.** Текущая автовысота считается только от содержимого
  (`measureRow()`), при мелком шрифте выходит ~4мм — меньше стандарта. См.
  [eskd-specification-header.md](eskd-specification-header.md).
- **Толщина линии — одна на всё, но только вне `FrameSpec`.** ГОСТ 2.303
  различает "толстую" (S = 0.5–1.4мм) и "тонкую" (S/3–S/2) линию.
  `FrameCell.borders` (`BorderWeight.THIN`/`THICK`, см.
  [eskd-title-block.md](eskd-title-block.md)) это умеет — используется в
  штампе и доп. графах. Но внешняя рамка страницы (`frameRectangle`) и
  сетка заголовка спецификации (`drawRichHeader`) по-прежнему рисуются
  одной константой `Styles.tableBorder` (2.0pt ≈ 0.7мм) — гэп закрыт
  частично, не для всего документа.

## Шрифты

- **GOST Type A всё ещё заглушка** (PT Sans Regular) — реального
  чертёжного шрифта Type A нет. См.
  [fonts-and-licensing.md](fonts-and-licensing.md).
- **Резолвинг шрифта по имени семейства пишется руками в каждом
  consumer'е** (сейчас — только `report-cli/Main.kt`). Нет общего
  механизма "зарегистрировать шрифт под именем семейства и получить
  resolver автоматически" — если появится второй реальный потребитель
  пайплайна, придётся либо копировать этот код, либо на этот момент вынести
  абстракцию.

## Отчёты и данные

- **`report-api` — контракт без реализации.** DTO и интерфейс `PdmClient`
  существуют, но нет ни одного реального HTTP-клиента — реального PDM
  сейчас нет для интеграции (подтверждено с пользователем явно, не
  предположение). Когда появится реальный endpoint — понадобится решить,
  какая HTTP/serialization библиотека (Ktor? kotlinx.serialization?
  что-то другое) — сейчас сознательно не выбрано, чтобы не тащить
  зависимости под несуществующий контракт.
- **`SpecificationItem` не содержит полей Формат/Зона/Примечание.** Реальная
  форма 1 ГОСТ 2.106 имеет эти графы, но текущая доменная модель
  (`report-data/SpecificationData.kt`) их не несёт — в `reports/specification/Specification.kt`
  эти три ячейки на каждой строке данных всегда пустые (`IrCell("")`).
  Расширение модели — когда появятся реальные данные с этими полями.

## Не начато (по dev-plan)

- **Фаза 7 (XLSX projection)** — сознательно отложена по решению пользователя
  ("Эксель — рано"), см. `../dev-plan-0.1.md`.
- **Determinism infra** (структурное сравнение Layout IR для regression) —
  сквозная задача из dev-plan, отдельно не реализована; фактическую
  повторяемость сейчас проверяют golden-снапшоты (SVG/PNG), не структурное
  сравнение самого Layout IR.
- **Реальная интеграция с PDM** — ждёт появления реального API.

## Прочее

- **Строковые литералы стилей** (`fontFamily`) защищены общими константами
  `FontFamilies` (см. [fonts-and-licensing.md](fonts-and-licensing.md)), но
  сам `TextStyle.fontFamily` остаётся простой `String`, не sealed-типом —
  теоретически ничто не мешает написать произвольную строку, которая ни на
  что не резолвится (упадёт в фоллбэк молча, не ошибкой). Полностью типобезопасным
  это сделать можно, но не сделано — trade-off между гибкостью (report
  builder может назвать любой шрифт) и безопасностью.
