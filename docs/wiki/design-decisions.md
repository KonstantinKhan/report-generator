# Ключевые решения и почему

Список решений, принятых по ходу разработки, с обоснованием. См. также
[known-gaps.md](known-gaps.md) — что осталось нерешённым осознанно.

## `Length` — fixed-point `Long`, не `Double`

`report-geometry/Length.kt`. Внутреннее представление — сотые доли
миллиметра (`raw: Long`). Не `Double`.

**Почему:** детерминизм (одни данные + одна версия движка = один и тот же
результат, независимо от JVM/платформы) плюс отсутствие накопления ошибки
округления через много операций сложения/вычитания при layout-вычислениях.
Double с этим не гарантирует байт-в-байт повторяемость между запусками.

## `PageFormat` — `data class`, не `enum`

Изначально (фаза 1) был `enum class PageFormat { A4, A3 }` в
`report-layout-ir`. Отрефакторено в `data class PageFormat(name, width,
height)` с константами `PageFormat.A4`/`PageFormat.A3` в
`report-geometry`.

**Почему:** (1) `report-ir` тоже должен уметь ссылаться на формат страницы
(DSL `pageSetup { format = ... }`), но не может зависеть от
`report-layout-ir` — значит формат должен жить в общей базе
(`report-geometry`), не в Layout IR. (2) Тестам пагинации нужны кастомные
крошечные форматы (например 80×40мм), чтобы форсировать разрыв страницы без
сотен строк данных — `enum` с фиксированным набором значений этого не даёт.

## `FontRegistry` хранит байты шрифта, не `PDFont`

`report-layout/FontRegistry.kt`. Регистрирует `ByteArray` по строковому id,
метод `loadInto(document, ref)` создаёт `PDFont` заново на каждый вызов.

**Почему:** объект `PDFont` в PDFBox привязан к конкретному `PDDocument`, в
котором он создан — его нельзя переиспользовать в другом документе.
Измеритель текста (`PdfBoxTextMeasurer`) и PDF-рендерер работают с РАЗНЫМИ
`PDDocument` (один — внутренний служебный для измерения, другой — реальный
выходной). Раз объект `PDFont` не переносится между ними, единственный
реальный источник истины — байты шрифта: оба потребителя грузят одни и те
же байты в свои документы и получают идентичные метрики. Гарантия
"измерение = рисование" держится на равенстве байтов, а не идентичности
объекта.

## Overflow policy — hard error, не best-effort

`LayoutOverflowException(elementPath, constraint, pageNumber, message)` в
`report-layout/LayoutEngine.kt`. Когда блок не влезает даже на чистую
страницу — исключение, а не тихая обрезка/сжатие.

**Почему:** инженерная документация не терпит тихих искажений (обрезанный
текст в документе по ЕСКД — дефект, не деградация). Explicit fail-fast
сразу указывает на проблему в данных/стилях/report builder'е, вместо
непредсказуемого визуального артефакта, замеченного постфактум. Совместимо
с идеей детерминизма — ошибка тоже часть детерминированного поведения:
одни данные either дают один Layout IR, either одну и ту же ошибку.

Известное ограничение: проверяется только **вертикальный** overflow (высота
строки/страницы). Горизонтальный (сумма ширин колонок больше ширины
контента) не проверяется — см. [known-gaps.md](known-gaps.md).

## `TextMeasurement.lines` — зачем список строк, а не только ширина/высота

`report-layout/TextMeasurer.kt`. Изначально `TextMeasurement` содержал
только `width/height/lineCount`. Расширено полем `lines: List<String>`.

**Почему:** Layout Engine должен разместить КАЖДУЮ строку переноса отдельным
`PositionedText` (у каждой своя `y`-позиция). Без реальных строк
переноса (не только их количества) невозможно понять, ЧТО писать на
каждой строке.

## `TextAlign` и `TextOrientation` — по-разному распределены между слоями

Разобрано подробно в [architecture.md](architecture.md#почему-textalign-и-textorientation-живут-по-разному).
Короткая версия: alignment — это только "какой `x` посчитать", никогда не
покидает report-layout. Orientation — это факт, важный для рисования, живёт
в обоих IR отдельными enum'ами (архитектурная граница не разрешает делить
один тип).

## Общие константы — не дублировать по модулям

Два случая, где одна и та же константа сначала завелась в двух местах
независимо, потом была схлопнута в одну:

- `BASELINE_RATIO = 0.8` — сначала был `private const val` в
  `report-render-svg` И отдельно в `report-render-pdf`. Перенесён в
  `report-layout-ir` как публичная `const val` — оба рендерера уже зависят
  от этого модуля, так что естественное место для константы, которую оба
  ДОЛЖНЫ использовать одинаково (иначе SVG и PDF рисовали бы текст с разным
  визуальным центрированием при повороте).
- `FontFamilies.GOST_TYPE_A` / `GOST_TYPE_B` — сначала строки-литералы
  `"GOST Type A"`/`"GOST Type B"` использовались независимо в
  `report-ir/Styles.kt` (где объявляется стиль) и в `report-cli/Main.kt`
  (где резолвится реальный шрифт по имени). Опечатка в любом месте раньше
  тихо приводила бы к неправильному шрифту без ошибки компиляции. Теперь
  обе стороны ссылаются на `report-ir.FontFamilies`.

Урок: если константа используется больше чем в одном месте и рассинхрон
даёт молчаливый неправильный результат (не ошибку компиляции) — заводить
её сразу в общем месте, не полагаться на "будем аккуратны".

## Rotation math для вертикального текста — разные знаки в SVG и PDF

Разобрано подробно в
[eskd-specification-header.md](eskd-specification-header.md#математика-поворота).
Кратко: SVG (`rotate(-90)`) и PDF (`Matrix.getRotateInstance(+90°)`) дают
ОДИНАКОВЫЙ визуальный результат при РАЗНЫХ знаках угла — потому что у SVG
ось Y направлена вниз и поворот по часовой стрелке считается положительным,
а у PDF ось Y направлена вверх и поворот считается по стандартной
математической (против часовой) конвенции. Оба renderer'а используют одну
и ту же `BASELINE_RATIO` для компенсации асимметрии ascent/descent шрифта
при центрировании — без этого текст визуально "съезжал" в сторону (реальный
баг, найденный и исправленный в процессе).
