# Ключевые решения и почему

Список решений, принятых по ходу разработки, с обоснованием. См. также
[known-gaps.md](known-gaps.md) — что осталось нерешённым осознанно.

Решения ветки `engine` (YAML-шаблоны, данные, таблица потока) собраны в конце страницы, раздел «Решения ветки `engine`».
Решения слоя до ветки (`Length`, `FontRegistry`, overflow, рамка) в силе; устаревшие подробности помечены баннерами
`Обновление` / `УСТАРЕЛО` у соответствующих разделов.

## `Length` — fixed-point `Long`, не `Double`

`report-geometry/Length.kt`. Внутреннее представление — сотые доли
миллиметра (`raw: Long`). Не `Double`.

**Почему:** детерминизм (одни данные + одна версия движка = один и тот же
результат, независимо от JVM/платформы) плюс отсутствие накопления ошибки
округления через много операций сложения/вычитания при layout-вычислениях.
Double с этим не гарантирует байт-в-байт повторяемость между запусками.

## `PageFormat` — `data class`, не `enum`

Изначально (фаза 1) был `enum class PageFormat { A4, A3 }` в
`report-layout-ir`. Отрефакторено в `data class PageFormat(name, width,
height)` с константами `PageFormat.A4`/`PageFormat.A3` в
`report-geometry`.

**Почему:** (1) `report-ir` тоже должен уметь ссылаться на формат страницы
(DSL `pageSetup { format = ... }`), но не может зависеть от
`report-layout-ir` — значит формат должен жить в общей базе
(`report-geometry`), не в Layout IR. (2) Тестам пагинации нужны кастомные
крошечные форматы (например 80×40мм), чтобы форсировать разрыв страницы без
сотен строк данных — `enum` с фиксированным набором значений этого не даёт.

## `FontRegistry` хранит байты шрифта, не `PDFont`

`report-layout/FontRegistry.kt`. Регистрирует `ByteArray` по строковому id,
метод `loadInto(document, ref)` создаёт `PDFont` заново на каждый вызов.

**Почему:** объект `PDFont` в PDFBox привязан к конкретному `PDDocument`, в
котором он создан — его нельзя переиспользовать в другом документе.
Измеритель текста (`PdfBoxTextMeasurer`) и PDF-рендерер работают с РАЗНЫМИ
`PDDocument` (один — внутренний служебный для измерения, другой — реальный
выходной). Раз объект `PDFont` не переносится между ними, единственный
реальный источник истины — байты шрифта: оба потребителя грузят одни и те
же байты в свои документы и получают идентичные метрики. Гарантия
"измерение = рисование" держится на равенстве байтов, а не идентичности
объекта.

## Overflow policy — hard error, не best-effort

`LayoutOverflowException(elementPath, constraint, pageNumber, message)` в
`report-layout/LayoutEngine.kt`. Когда блок не влезает даже на чистую
страницу — исключение, а не тихая обрезка/сжатие.

**Почему:** инженерная документация не терпит тихих искажений (обрезанный
текст в документе по ЕСКД — дефект, не деградация). Explicit fail-fast
сразу указывает на проблему в данных/стилях/report builder'е, вместо
непредсказуемого визуального артефакта, замеченного постфактум. Совместимо
с идеей детерминизма — ошибка тоже часть детерминированного поведения:
одни данные either дают один Layout IR, either одну и ту же ошибку.

Известное ограничение: проверяется только **вертикальный** overflow (высота
строки/страницы). Горизонтальный (сумма ширин колонок больше ширины
контента) не проверяется — см. [known-gaps.md](known-gaps.md).

## `TextMeasurement.lines` — зачем список строк, а не только ширина/высота

`report-layout/TextMeasurer.kt`. Изначально `TextMeasurement` содержал
только `width/height/lineCount`. Расширено полем `lines: List<String>`.

**Почему:** Layout Engine должен разместить КАЖДУЮ строку переноса отдельным
`PositionedText` (у каждой своя `y`-позиция). Без реальных строк
переноса (не только их количества) невозможно понять, ЧТО писать на
каждой строке.

## `TextAlign` и `TextOrientation` — по-разному распределены между слоями

Разобрано подробно в [architecture.md](architecture.md#почему-textalign-и-textorientation-живут-по-разному).
Короткая версия: alignment — это только "какой `x` посчитать", никогда не
покидает report-layout. Orientation — это факт, важный для рисования, живёт
в обоих IR отдельными enum'ами (архитектурная граница не разрешает делить
один тип).

## Общие константы — не дублировать по модулям

Два случая, где одна и та же константа сначала завелась в двух местах
независимо, потом была схлопнута в одну:

- `BASELINE_RATIO = 0.8` — сначала был `private const val` в
  `report-render-svg` И отдельно в `report-render-pdf`. Перенесён в
  `report-layout-ir` как публичная `const val` — оба рендерера уже зависят
  от этого модуля, так что естественное место для константы, которую оба
  ДОЛЖНЫ использовать одинаково (иначе SVG и PDF рисовали бы текст с разным
  визуальным центрированием при повороте).
- `FontFamilies.GOST_TYPE_A` / `GOST_TYPE_B` — сначала строки-литералы
  `"GOST Type A"`/`"GOST Type B"` использовались независимо в
  `report-ir/Styles.kt` (где объявляется стиль) и в `report-cli/Main.kt`
  (где резолвится реальный шрифт по имени). Опечатка в любом месте раньше
  тихо приводила бы к неправильному шрифту без ошибки компиляции. Теперь
  обе стороны ссылаются на `report-ir.FontFamilies`.

Урок: если константа используется больше чем в одном месте и рассинхрон
даёт молчаливый неправильный результат (не ошибку компиляции) — заводить
её сразу в общем месте, не полагаться на "будем аккуратны".

## `FrameSpec`/`FrameCell` вместо `TitleBlockSpec`

> **Обновление (2026-10-03).** Содержимое `FrameSpec` теперь строится из YAML
> (`gost-spec.yaml`, модуль `report-template`), а не из констант в `FrameSpecs.kt`.
> Сам тип `FrameSpec`/`FrameCell` остался как внутренний формат между шаблоном и
> раскладкой. Динамические ячейки больше не ссылаются на enum `FrameField`: `FrameCell.Dynamic` несёт путь
> бинда (`doc.designation`, `page.number`), `FrameBindings` стал готовым `DataContext` на два поля. См.
> [template-yaml.md](template-yaml.md).

`report-ir/Frame.kt` + `report-ir/frames/FrameSpecs.kt`. Разобрано подробно
в [eskd-title-block.md](eskd-title-block.md). Коротко: `TitleBlockSpec`
(designation/name/sheetsTotal) не могла выразить реальную геометрию
основной надписи ЕСКД — сетку ячеек с объединениями, разной толщиной линий
по сторонам, вертикальным текстом. `FrameSpec` — обычный список ячеек
(`Constant`/`Dynamic`) с `Rect` относительно угла блока, переиспользует уже
существующий `geometry.Rect` вместо отдельного типа из наброска в
architecture-0.2.md §34.

## `renderPages()` — два прохода, не потоковая отрисовка chrome

`report-layout/LayoutEngine.kt`. Раньше рамка/header/штамп каждой страницы
дорисовывались сразу по её завершении. Как только штампу понадобилось
показывать вычисляемые `SHEET_NUMBER`/`SHEETS_TOTAL` — это стало
невозможно для страницы 1 (общее число страниц ещё не известно в момент её
отрисовки). Решение — собрать контент всех страниц первым проходом (ровно
та же логика пагинации, что и раньше), потом вторым проходом дорисовать
chrome, зная `totalPages`. Подробности — [eskd-title-block.md](eskd-title-block.md).

## Границы ячеек рамки — вручную удлинённые `Line`, не `Rectangle`

`report-layout/LayoutEngine.kt`, `drawFrame()`. Нужны разные толщины по
четырём сторонам одной ячейки (`CellBorders`) — `Rectangle` из
`report-layout-ir` несёт только одну `BorderStyle` на весь прямоугольник,
не подходит. Четыре независимых `Line` с дефолтным `butt`-cap на
несвязанных отрезках не докрывают маленький квадрат в углу (реальный баг,
найден кропом PDF в высоком DPI, не чтением кода и не превью 1:1 —
см. [eskd-title-block.md](eskd-title-block.md)). Фикс — каждая линия
удлиняется на половину своей же толщины за оба конца (ручной аналог
`stroke-linecap: square`). Понятие "cap" в `LineStyle` не заводилось —
специфично для того, как считаются координаты именно здесь.

## `BorderWeight.NONE` — не только тонкая/толстая

`report-ir/Frame.kt`. Добавлено ради `belowFrameNotes` ("Копировал"/
"Формат" под рамкой) — первые ячейки `FrameSpec`, которым не нужен бордер
вообще. Ширина 0 у `Line` — не то же самое, что "не рисовать": PDF/SVG
трактуют перо нулевой ширины как тончайшую видимую линию, не как
невидимую. `drawFrame()` поэтому просто не добавляет сторону с `NONE` в
список линий, а не рисует её прозрачной шириной. Подробности —
[eskd-title-block.md](eskd-title-block.md).

## Rotation math для вертикального текста — разные знаки в SVG и PDF

Разобрано подробно в
[eskd-specification-header.md](eskd-specification-header.md#математика-поворота).
Кратко: SVG (`rotate(-90)`) и PDF (`Matrix.getRotateInstance(+90°)`) дают
ОДИНАКОВЫЙ визуальный результат при РАЗНЫХ знаках угла — потому что у SVG
ось Y направлена вниз и поворот по часовой стрелке считается положительным,
а у PDF ось Y направлена вверх и поворот считается по стандартной
математической (против часовой) конвенции. Оба renderer'а используют одну
и ту же `BASELINE_RATIO` для компенсации асимметрии ascent/descent шрифта
при центрировании — без этого текст визуально "съезжал" в сторону (реальный
баг, найденный и исправленный в процессе).

## Решения ветки `engine`

Хронология и хеши коммитов: [changelog-engine.md](changelog-engine.md). Ниже то, что решено и почему.

### YAML описывает ЧТО, алгоритм остаётся Kotlin

Шаблон задаёт структуру листа, стиль таблицы и правила, как данные попадают в таблицу. Измерение текста, перенос слов,
пагинация, цепочки `keep`, дозаполнение и два прохода `renderPages()` остались кодом `report-layout`.

**Почему:** алгоритм раскладки это то, что нельзя «настроить» в конфиге без языка программирования, а язык в конфиге
хуже кода в тестируемости и диагностике. Граница «что/как» держит golden-тесты осмысленными: меняется YAML — меняется вид,
меняется алгоритм — видно в эталонах всех шаблонов сразу. Шаблоны пишет инженер без знания Kotlin, движок правит
разработчик.

### Закрытые структурные операции, без языка выражений

`where`, `sortBy`, `groupBy`, `computed` (`multiply` / `add` / `subtract` / `divide`, `sequence`), `cases`, `totals` это
фиксированный набор ключей; предикаты структурные (`{field, eq|ne|in|isNull|notNull}`, `and` / `or` / `not`), строковых
выражений вида `${a} * ${b}` нет.

**Почему:** каждая операция проверяется при загрузке с YAML-путём (тип поля, цикл зависимостей, неизвестное имя с подсказкой),
чего у строки-выражения без собственного парсера и типизатора не будет. Нет скриптов — нет неограниченного поведения и
вопроса безопасности шаблонов. Расчёт точный (`BigDecimal`, явные `scale` + `rounding`), результат детерминирован.
Цена: новая операция это код; пока набор покрывает спецификацию и ведомость покупных (см. [known-gaps.md](known-gaps.md)).

### Типизированный контекст данных и контракт при загрузке; нет значения = ошибка

Данные шаблона это `DataContext` со схемой (`DataSchema`): типы `String` / `Integer` / `Decimal` / `Date` / `Boolean` /
`Enum` / `List` / `Record`. `TemplateContract` сверяет каждый bind с схемой до раскладки (путь существует, значение
скалярное, `format` подходит типу). Поле без значения при раскладке это ошибка; пустая ячейка допускается только явным
`optional: true`.

**Почему:** прежний `${...}` оставлял неизвестный путь текстом в документе: опечатка попадала на чертёж (то же правило, что
у overflow policy: инженерный документ не терпит тихих искажений). Явный `optional` делает «поля может не быть»
осознанным решением шаблона, а не следствием молчаливого пустого значения. `format` (`pattern`, `locale`, `rounding`)
задаётся в шаблоне, потому что формат вывода это часть вида документа. `locale` по умолчанию нет (точка), `ru` пишется явно.
Для `--data` тип выводится по значению, тег (`!str`, ...) задаёт его принудительно; смешанные типы в одном поле это ошибка
с обеими строками, а не молчаливая подмена (`Integer` + `Decimal` сливаются в `Decimal`).

### Адаптер данных на тип отчёта

`reports/specification` содержит только адаптер `SpecificationData.toDataContext()` / `itemRecords()` (схема `doc` + `item`
и сырые типизированные записи) и вызов `FlowTables.build`. Позицию, группы, формат количества, правило единицы считает YAML.

**Почему:** каждый новый тип отчёта (ведомость, перечень) приносит свой адаптер и свой YAML, а движок и шаблонный слой не
меняются. Раньше `Specification.kt` держал `GROUPS`, `item.position`, `item.quantityText`: правило таблицы жило в коде отчёта и
дублировалось бы в каждом следующем. Миграцию страхует parity-тест: `IrTable` из YAML равен таблице прежнего кода
(`LegacySpecificationTable`, оставлена только в тестах как эталон).

### Id слотов связываются с `FrameSpec` только на пути спецификации

Блоки `stamp`, `continuationStamp`, `leftMargin`, `belowFrame`, `specLeft`, `mainTitleRight` получают размер своего
`FrameSpec` (и убираются при пустом слоте) только при `PageSetup.bindStaticSlots = true` (боевой движок). В пути
`TemplateMain` (`bindStaticSlots = false`) id свободны и `reserves` работает у любого блока.

**Почему:** на пути своего шаблона блок с именем `stamp` молча терялся (слот без `FrameSpec` пуст), и таблица потока ехала под
штамп. Запрещать «красивые» имена в чужих шаблонах хуже, чем ограничить магию слотов путём, где она нужна.

### Нижняя граница последней строки рисуется всегда; `remainder: stretch | gap`

Высота страницы под последней строкой данных не кратна `rowHeight`. `stretch` (по умолчанию) поглощает остаток последней
пустой строкой, страница закрыта до низа; `gap` оставляет все пустые строки равными `rowHeight`, остаток зазором над штампом.
Нижняя граница последней пустой строки рисуется в обоих режимах.

**Почему:** раньше при наличии рамки движок убирал нижнюю границу последней строки: слева от штампа первой страницы таблица
оставалась «открытой». Всегда рисовать проще и предсказуемее (решение владельца); где граница ложится на толстую рамку
или штамп, она невидима. Цена: в 8 golden-файлах спецификации добавились линии (миграция в [changelog-engine.md](changelog-engine.md)).
`gap` нужен формам, где все строки обязаны быть одной высоты.

### Нумерация физических строк делает раскладка

`${line.number}` ставит `report-layout` вторым проходом по страницам, `FlowTables` оставляет ячейку пустой и кладёт
настройки в `IrTable.lineNumbers`.

**Почему:** сколько физических строк займёт запись, известно только после переноса слов по ширине колонки, то есть в
раскладке. Номер, посчитанный при сборке данных, разошёлся бы с реальным видом. Второй проход (страницы сначала
раскладываются, потом рисуются по порядку) нужен, чтобы блок, перенесённый на следующую страницу цепочкой `keepWithNext`,
получил верный номер: без пропусков и повторов. `pos` (`computed.sequence`) нумерует ЗАПИСИ и остаётся.

### Жёсткий перенос `\n` в ячейках данных

`\n` в тексте ячейки строки (литерал или значение из данных) режет текст на сегменты, каждый переносится по словам отдельно;
пустой сегмент это пустая физическая строка, завершающие переводы строки отбрасываются, `\r\n` и `\r` равны `\n`.

**Почему:** значение из данных может нести собственные переводы строки (примечание в несколько строк), а `manualLines` (шапка)
отключает авто-перенос; для данных нужен перенос по словам внутри сегмента. Измеритель текста (`PdfBoxTextMeasurer`) делит по `\n`, поэтому `IrCell` и всё, что
работает со строками (`stick`, цепочки `keep`, нумерация, разрыв записи страницей), ничего о `\n` не знает и не менялось.

### Сборочные единицы поддерживаются; единица измерения только у материалов

`mapItemKind` в `report-loodsman` отображает `Сборочная единица` в `ASSEMBLY` (раньше такие дети терялись, группа сборочных
единиц не могла заполниться). Единица измерения выводится только у `MATERIAL` (правило `cases` ячейки `note` в YAML).

**Почему:** по ГОСТ Р 2.106-2019 штучный учёт сборочных единиц, деталей и стандартных изделий идёт без единицы, она нужна
только материалам (кг, м); колонка «Кол.» 10 мм не вмещает значение и единицу. Правило в YAML, а не в коде, потому что оно
относится к виду формы, а не к данным.

### Строки таблицы не теряются молча

Каждое значение enum схемы должно быть в `groupBy.order` или `groupBy.omit`, иначе ошибка контракта; сортировка устойчивая,
строки не пропадают молча.

**Почему:** потеря позиции спецификации хуже ошибки сборки; `omit` делает сознательный отброс явным.
