# Заголовок таблицы спецификации (ЕСКД / ГОСТ Р 2.106-2019)

> **Частично устарело (2026-10-03).** Геометрия формы 1, математика поворота и баг со смещением остаются верными. Изменилось:
> заголовок спецификации теперь описан в YAML (`gost-spec.yaml`, блок `body`, `table.header`), а `IrTableHeader` собирает
> `FlowTables` (есть `repeat`, а для многоуровневой шапки сетка `IrHeaderGrid`, см. [template-yaml.md](template-yaml.md#многоуровневая-шапка-headerrows-span-rowspan));
> высота строки данных теперь фиксирована (`rowHeight: 8`). DSL `header(...) { cell(...) }` ниже остался как исторический
> способ собрать `IrTableHeader` вручную. Обе формы рисует `drawRichHeader` через `IrTableHeader.asGrid()`.

Как устроена "форма 1" — заголовок таблицы спецификации с колонками
Формат/Зона/Поз./Обозначение/Наименование/Кол./Примечание, часть из которых
читается вертикально снизу вверх.

## Что подтверждено чтением реального стандарта

Прочитан фактический текст ГОСТ Р 2.106-2019, приложение А (форма 1), не
пересказ — см. `/tmp/gost-2106.pdf` в истории сессии (скачан с
files.stroyinf.ru). Диаграмма формы 1 даёт:

```text
margin | Формат | Зона | Поз. | Обозначение | Наименование | Кол. | Примечание | margin
  20   |   6    |  6   |  8   |     70      |      63      |  10  |     22     |   5
```

Сумма 20+6+6+8+70+63+10+22+5 = 210мм = ширина A4. Высота строки заголовка —
**15мм**. Это ровно те цифры, что реализованы в
`reports/specification/Specification.kt`.

Стандарт **не регламентирует размер шрифта** — только геометрию ячеек.
Размер выбирается из стандартного ряда ГОСТ 2.304 (1.8, 2.5, 3.5, 5, 7, 10,
14, 20, 28, 40мм) и подбирается по факту помещения в ячейку. Самая узкая
графа (Формат/Зона) — 6мм; при 3.5мм повёрнутый текст встал бы впритык к
рамке, поэтому для заголовка изначально взяли 2.5мм (позже пользователь
поднял до 3.5мм для body-текста заголовка — сейчас `Styles.tableHeader`
имеет `fontSizeMm = 3.5`, см. `report-ir/Styles.kt`).

Также найдено: форма 1 требует **минимум 8мм** высоты строки данных. Автовысота строки
при мелком шрифте давала около 4мм. **Закрыто:** таблица спецификации теперь с фиксированной высотой строки
(`rowHeight: 8` в `gost-spec.yaml`, см. [specification-table-format.md](specification-table-format.md)).

## Модель данных

`report-ir/Ir.kt`:

```kotlin
enum class TextOrientation { HORIZONTAL, VERTICAL_BOTTOM_TO_TOP }
enum class TextAlign { LEFT, CENTER }

data class IrCell(
    val text: String,
    val style: TextStyle = Styles.tableText,
    val orientation: TextOrientation = TextOrientation.HORIZONTAL,
    val align: TextAlign = TextAlign.LEFT,
    val manualLines: List<String>? = null
)

data class IrTableHeader(
    val cells: List<IrCell>,
    val height: Length? = null   // null = автовысота (старое поведение)
)
```

DSL (`DocumentBuilder.kt`, `HeaderBuilder`):

```kotlin
header(height = 15.mm) {
    cell("Формат", orientation = TextOrientation.VERTICAL_BOTTOM_TO_TOP)
    cell("Зона", orientation = TextOrientation.VERTICAL_BOTTOM_TO_TOP)
    cell("Поз.", orientation = TextOrientation.VERTICAL_BOTTOM_TO_TOP)
    cell("Обозначение")
    cell("Наименование")
    cell("Кол.", orientation = TextOrientation.VERTICAL_BOTTOM_TO_TOP)
    cell("Примечание", manualLines = listOf("Приме-", "чание"))
}
```

`HeaderBuilder.cell()` по умолчанию берёт `Styles.tableHeader` (шрифт GOST
Type B) и `TextAlign.CENTER` — так что заголовку не нужно указывать это на
каждой ячейке. Обычные строки данных (`GroupBuilder.row()`) остаются на
`Styles.tableText` / `TextAlign.LEFT` без изменений.

`manualLines` — явный список строк, минующий автоматический перенос по
ширине. Единственный способ получить перенос через дефис ("Приме-"/"чание")
— система не умеет расставлять переносы сама (это была бы отдельная,
существенно более сложная фича — словари переноса слов; сознательно не
реализовано, см. [known-gaps.md](known-gaps.md)).

## Путь через Layout Engine: два разных рендер-пути для заголовка

`report-layout/LayoutEngine.kt`, `buildHeaderLayout()`:

- `header.height == null` → старый путь: `measureRow()` + `drawRow()`,
  автовысота, только горизонтальный текст. Используется старыми вызовами,
  где никто не указывал `height` явно — ничего не ломается.
- `header.height != null` → новый путь: `drawRichHeader()` — по каждой
  ячейке отдельно: рамка + текст с учётом `orientation`/`align`/`manualLines`,
  центрирование внутри фиксированной высоты.

Каждая ячейка заголовка получает свою рамку (`Rectangle`) с толщиной
`Styles.tableBorder` — то есть заголовок рисуется как настоящая сетка 7
ячеек, не просто текст на пустом фоне.

## Математика поворота

Вертикальный текст (`VERTICAL_BOTTOM_TO_TOP`) должен читаться снизу вверх,
с "низом" глифов (базовой линией) у правого края колонки — так задал
пользователь, это стандартная ЕСКД-конвенция для узких граф.

### Layout-уровень (report-layout, `drawVerticalHeaderCell`)

Бокс текста в обычных (неповёрнутых) осях страницы:
- `width` = высота одной строки текста (`lineHeight`) — это "толщина" на
  странице
- `height` = измеренная длина текста (`measurement.width`) — это "длина"
  вдоль вертикали
- центрируется и по ширине колонки, и по высоте строки заголовка

### Render-уровень — разные знаки в SVG и PDF

**SVG** (`rendersvg/SvgRenderer.kt`): `rotate(-90)`. У SVG ось Y направлена
вниз, поворот по часовой стрелке — положительный угол. `-90°` — против
часовой. Локальное `+x` (направление чтения текста) отображается на
"вверх" страницы, локальное `+y` (ниже базовой линии, то есть descent) —
на "вправо". Это и даёт "снизу вверх, низ глифов справа".

**PDF** (`renderpdf/PdfRenderer.kt`): `Matrix.getRotateInstance(+90°)`. PDF
использует ось Y вверх и стандартную математическую конвенцию (положительный
угол — против часовой). Тот же зрительный результат достигается
ПРОТИВОПОЛОЖНЫМ по знаку углом — не баг, а следствие разных конвенций осей.

### Реальный баг, который был найден и исправлен

Первая версия анкорила точку поворота в геометрический центр бокса
(`rect.width / 2`). У шрифта ascent (выше базовой линии) больше descent
(ниже) — при повороте ascent уходит в одну сторону сильнее, чем descent в
другую, и центрирование "50/50" визуально сдвигало текст. Пользователь
заметил ("Формат, Зона, Поз., Кол. съехали влево") на реальном PDF.

Исправление: анкор ставится на `rect.width * BASELINE_RATIO` (та же
константа 0.8, что и для обычного горизонтального текста — только теперь
общая, вынесена в `report-layout-ir`, см.
[design-decisions.md](design-decisions.md#общие-константы--не-дублировать-по-модулям)),
а не на 50%. Это даёт ascent'у пропорционально больше места, и глифы
визуально попадают в центр колонки.

**Мораль:** математику поворота и анкоринга нельзя надёжно проверить чтением
кода — нужен реальный рендер и взгляд на него. Эта фича делалась руками
(без делегирования субагентам) именно по этой причине.
