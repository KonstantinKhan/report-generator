# Основная надпись и доп. графы (ЕСКД / ГОСТ 2.104)

Как устроена рамка/штамп после реализации `FrameSpec` (architecture-0.2.md
§34) — модель, геометрия двух конкретных пресетов, и два реальных бага,
найденных и исправленных в процессе (см. `git log` коммит
`feat: implement FrameSpec/StampSpec (§34)`).

## Модель

`report-ir/Frame.kt`:

```kotlin
enum class FrameField { DESIGNATION, NAME, SHEET_NUMBER, SHEETS_TOTAL }
enum class BorderWeight { NONE, THIN, THICK }

data class CellBorders(
    val top: BorderWeight = THICK,
    val right: BorderWeight = THICK,
    val bottom: BorderWeight = THICK,
    val left: BorderWeight = THICK
)

sealed interface FrameCell {
    val rect: Rect   // относительно левого верхнего угла блока, не страницы
    val style: TextStyle
    val align: TextAlign
    val borders: CellBorders
    val orientation: TextOrientation

    data class Constant(..., val text: String) : FrameCell
    data class Dynamic(..., val field: FrameField) : FrameCell
}

data class FrameSpec(val size: Size, val cells: List<FrameCell>)
data class FrameBindings(val designation: String? = null, val name: String? = null)
```

Отличие от наброска в architecture-0.2.md §34: там был отдельный
`FrameCellRect`. В реализации используется обычный `geometry.Rect` — он уже
общий для `report-ir`/`report-layout-ir` (см. §21/§23 архитектуры), заводить
для рамки ещё один прямоугольный тип избыточно.

`SHEET_NUMBER`/`SHEETS_TOTAL` **не** входят в `FrameBindings` — их считает
Layout Engine (см. ниже), это не входные данные отчёта, а результат
пагинации.

## Пресеты (`report-ir/frames/FrameSpecs.kt`)

### `firstPageStamp` — основная надпись, 185×40мм

Только первая страница. Две независимые под-сетки одна над другой:

- **Заголовочная полоса** (0–15мм): `Изм`/`Лист`/`№ докум.`/`Подп.`/`Дата` —
  каждая колонка физически СВОЯ ОДНА ячейка на все 15мм (не три ряда), плюс
  `Dynamic(DESIGNATION)` на 120мм, тоже на все 15мм.
- **Сигнатурный блок** (15–40мм): `Разраб.`/`Пров.`/`Н. контр.`/`Утв.` в
  первой колонке (17мм), `Dynamic(NAME)` — одна ячейка 70×25мм (строки 4–8),
  `Лит.`/`Лист`/`Листов` в строке 4, `Dynamic(SHEET_NUMBER)`/`Dynamic(SHEETS_TOTAL)`
  в строке 5. Границы между строками 4–8 внутри первых 4 колонок —
  тонкие сверху/снизу, толстые слева/справа (ГОСТ 2.303); все прочие толстые.

Якорь — правый нижний угол ОСНОВНОЙ РАМКИ (не страницы): `frameOrigin()` в
`LayoutEngine.kt` считает `x = format.width - margins.right - size.width`,
`y = format.height - margins.bottom - size.height`. Для A4 с полями отчёта
(20/5/5/5мм слева/сверху/справа/снизу) содержательная ширина ровно 185мм —
поэтому штамп занимает всю ширину, не только "правый" визуально.

### `leftMarginTable` — доп. графы, 12×135мм, повёрнута на 90°

Полоса `Инв. № подл.`/`Подл. и дата`/`Взам. инв. №`/`Инв. № дубл.`/
`Подп. и дата`, читается снизу вверх (та же конвенция, что и вертикальные
колонки заголовка спецификации — см. eskd-specification-header.md). Каждая
ячейка — не блок с "поворотом", а обычная **узкая и высокая** `FrameCell` с
`orientation = VERTICAL_BOTTOM_TO_TOP`: геометрия уже "повёрнута" в
координатах (width = толщина 5/7мм, height = длина вдоль края 25/35мм), сам
поворот текста делает уже существующий `drawVerticalHeaderCell` — переиспользован
как есть, никакой новой ротационной математики не понадобилось.

Порядок вдоль полосы (сверху вниз в локальных координатах блока / снизу
вверх на странице — `Инв. № подл.` физически ближе всего к углу листа):
`Подп. и дата`(35) → `Инв. № дубл.`(25) → `Взам. инв. №`(25) →
`Подл. и дата`(25) → `Инв. № подл.`(25). Поперёк: подписанная 5мм-колонка
первая (у края листа), пустая 7мм-колонка за ней, у самой рамки.

**Якорь — снаружи основной рамки**, не внутри: `leftMarginFrameOrigin()`
даёт `x = margins.left - size.width` (полоса торчит в левое поле, правым
краем впритык к рамке СНАРУЧИ) и `y = format.height - margins.bottom -
size.height` — низ полосы совпадает с низом самой рамки (5мм от края
листа), тем же способом, что и у штампа. Так как полоса снаружи рамки, она
физически не в том же x-диапазоне, что штамп (штамп — `x∈[20,205]`, полоса —
`x∈[8,20]`) — пересечения нет даже при полной высоте 135мм.

Первая версия якорила полосу ВНУТРИ рамки (у угла), потом её же низом к
верху штампа — обе оказались неверны (см. история правок в PR/коммите):
пользователь явно попросил "снаружи рамки" и "5мм от нижнего края листа".

### `belowFrameNotes` — "Копировал"/"Формат", 120×5мм, без границ

Две обычные горизонтальные подписи под рамкой, в собственном нижнем поле
листа (между низом рамки и физическим краем страницы — те же 5мм, что и
`margins.bottom`). В отличие от всех прочих ячеек рамки — **без бордера
совсем**, отсюда `BorderWeight.NONE` (см. ниже).

Якорь `belowFrameOrigin()` — правый край блока у правого края ЛИСТА
(`x = format.width - size.width`), низ блока у низа листа
(`y = format.height - size.height`). Локальные координаты внутри блока
читаются как "расстояние от правого края листа, зеркально": ячейка на
`local x=30` (центр) оказывается в 90мм от правого края, на `local x=90` —
в 30мм. Оба пресета — `Копировал` (по требованию ~90мм) и `Формат` (~30мм)
— заданы именно так, точность проверена тестом
(`FrameSpecsTest`, через обратный пересчёт `size.width - x - width/2`).

## `BorderWeight.NONE` — ячейка совсем без рамки

Понадобилось для `belowFrameNotes`: до этого `CellBorders` могла быть
только тонкой или толстой, но не отсутствующей — а простой подписи под
рамкой бордер не нужен вообще. `borderLineStyle(NONE)` даёт `width = 0`, но
рисовать линию нулевой ширины всё равно неверно (в PDF ширина 0 у пера
означает "тончайшая видимая линия", не "невидимая" — так что нулевая
ширина не значит невидимость). Поэтому в `drawFrame()` сторона с `NONE`
просто не добавляется в список линий (`buildList` с условием), а не
рисуется прозрачной.

## Layout Engine: два прохода вместо потокового рисования

До этой фичи `renderPages()` рисовал chrome (рамку страницы, header, штамп)
**сразу**, как только страница считалась завершённой — то есть в момент
отрисовки страницы 1 общее число страниц ещё не известно. Штампу же нужно
показать `SHEETS_TOTAL` — посчитать его в этот момент физически нельзя.

Решение — два прохода:

1. Первый проход, как и раньше, считает пагинацию/высоты, но кладёт строки
   в `List<MutableList<PageElement>>` (по списку на страницу) БЕЗ chrome.
   Решения о переносе страниц не меняются вообще — меняется только момент
   отрисовки рамки/штампа.
2. После цикла `totalPages` известен. Второй проход добавляет chrome
   каждой странице; штамп и доп.графы — только на странице 1, с
   `resolveBindings(bindings, pageNumber, totalPages)`.

## Баг: маленький квадратный вырез на внешних углах ячеек

`drawFrame()` рисует границы каждой ячейки как 4 независимых `Line`
(`report-layout-ir` не даёт цвет линии caps/join — только `width`+`color`),
не единый `Rectangle`-путь (это специально: нужны разные толщины по
сторонам, `Rectangle` несёт только одну). У `Line` нет понятия "cap" —
рендерится с дефолтным `butt` (что в SVG, что в PDFBox), а несвязанные
отрезки без общего пути не получают miter-соединения в углах.

Математически: горизонтальная линия покрывает `y ∈ [top-w/2, top+w/2]`
только для `x` НАЧИНАЯ со своей левой точки — левее неё (на диагонали за
углом) она ничего не красит. Вертикальная линия аналогично не докрашивает
выше своей верхней точки. На пересечении остаётся непрокрашенным маленький
квадрат `w/2 × w/2` ровно в диагональном "внешнем" углу — визуально
ступенька/вырез, особенно заметная на свободных (не примыкающих к соседним
ячейкам) углах составного блока, где сосед не докрашивает эту область сам.

Найдено не чтением кода, а рендером в PDF и покадровым кропом через
`pdftoppm -r 800 -x ... -y ... -W ... -H ...` — на превью в 1:1 масштабе
дефект невидим, разница в доли миллиметра.

**Фикс** — ручной аналог `stroke-linecap: square`: каждая из 4 линий
удлиняется на половину **своей же** толщины за оба конца (`halfWidth()` в
`LayoutEngine.kt`). Работает и для смешанных углов (тонкая встречается с
толстой) — линия с большей шириной перекрывает нужную область своей же
половиной, независимо от толщины соседней. Отдельного понятия "cap" в
`LineStyle` заводить не стал — это чисто про то, как считаются координаты
конкретно для рамки ячеек, не общее свойство линии в Layout IR.

## Что не входит

- `leftMarginTable`/`firstPageStamp`/`belowFrameNotes` — только первая
  страница. Рамка для
  continuation-страниц (§34.3 архитектуры — независимый пресет) не
  запрошена и не сделана.
- Толщина линии (`BorderWeight`) смоделирована только в `FrameCell`. Сетка
  заголовка спецификации (`drawRichHeader`) и внешняя рамка страницы
  (`frameRectangle`) по-прежнему рисуются одной толщиной
  (`Styles.tableBorder`) — старый гэп из known-gaps.md закрыт частично, не
  целиком.
- Резервирование ширины контента под `leftMarginTable` не сделано — она
  вне рамки, так что с содержимым таблицы не пересекается никогда (в
  отличие от более ранней версии, где она была внутри).
